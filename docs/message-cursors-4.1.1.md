# 4.1.1 消息游标修复

2026-10-06，真实事件验收发现：补齐新分库密钥后，已有状态没有该消息表游标，代码以零游标读取历史；每轮只读一页就推进整个会话时间，余下消息要等会话再次变化才能读取。用户确认缺失游标应从最新位置开始，已有游标则持续分页。

本次为客户端本地应用 4.1.0 → 4.1.1 PATCH，不改变消息事件、查询接口、配置格式或依赖。正式安装清单使用 Python 运行时，不发布原生可执行文件。

## 修正

- 缺失表游标：读当前最新 `(create_time, local_id)` 并建立基线；已有历史不发送。空表基线为零，之后的首条消息正常采集。
- 已有游标：固定本轮上界，再以有界页读取到该位置。分页游标按时间与本地 ID 排序，兼容同秒多条消息。
- 整页被 outgoing 过滤也推进扫描游标；发送失败不越过失败消息、不推进会话时间，重启从最后接受的位置续传。
- 本轮开始后新增的消息留到后续轮询，不无限追赶消息流。快照不可读时不建立伪造的零游标。

## 已受影响设备恢复

升级保留有效游标，不自动将所有设备重置到最新。已经被旧版错误写入历史游标的设备需要单独恢复，不能仅靠新版本的“缺少游标”规则识别。

本次验收设备已暂停微信 messageReceived 上传。先备份状态与未确认事件，按用户“不补投”的要求仅丢弃本次已识别的历史事件；用应用现有 `run --reset-state --once` 功能重新建立当前基线。恢复期间保持上传关闭，确认基线和队列后再恢复原上传权限。联系人状态及其他应用事件不在清理范围。旧验收消息已经成为基线前历史，恢复后用新消息重新验收。

真实 SQLite 回归覆盖缺失游标、持久化重启、空表首条消息、整页/跨页积压、同秒消息、整页过滤、分页中新消息到达、快照不可读和实际消息循环中途发送失败后的续传。运行完整 Python、Node、保留 Rust 测试、版本和归档检查；发布后分别验证来源版本、市场审核与设备运行状态。
