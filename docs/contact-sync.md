# 联系人增量同步协议

4.0.0 是不兼容的联系人事件协议变更。旧事件
`contactSnapshotChanged` 的自动 `started/contact/completed` 广播被
`contactsChanged` 替代，不能作为兼容补丁直接安装到旧消费者环境。
当前用户已于 2026-10-01 单独确认 4.0.0（MAJOR）。
版本从已冻结待审的 3.1.10 演进，公开市场此前为 3.1.9；安装推广仍须先完成消费者适配和切换验证。

## Connector 行为

- 从本机取得完整且一致的联系人列表，再按账号和联系人 ID 比较业务字段。
  文件时间和大小只属于读取快照的检查点，不决定哪些联系人需要上报。
- 比较字段为 `contactId`、`displayName`、`nickName`、`remark`、`sourceDeleted`。
  排序、数据库重写、文件时间变化，以及不参与同步的字段变化均不产生事件。
- 每个账号首次使用新协议时发送 `mode=initial` 的批次。每批最多 200 个联系人，
  JSON UTF-8 payload 不超过 64 KiB；超大单条明确失败，不截断或丢弃。
  空通讯录也产生一个空初始化批次。1 万联系人通常是 50 个批次，而非 1 万次工作流启动。
- 初始化之后使用 `mode=delta`，只包含新增和字段有变化的联系人。
  只有一个联系人变化时只发送一个批次、一个联系人；没有变化时不发送事件。
- 联系人未出现在本轮读取结果中不表示解除好友关系，不生成删除操作，也不丢弃已有比较基线。
  `sourceDeleted` 仅忠实表达源表的删除标记；接收端不得据此删除 CRM 线索或历史记录。
- `getContactSnapshot` 仍是显式、分页的只读查询方法；不再因为该快照 token 改变而自动全量广播。

## 事件契约

完整 JSON Schema 位于 `connector.json.events`，与 `bridge.py` 中的合同由测试核对。

| 字段 | 含义 |
| --- | --- |
| `protocolVersion` | 固定为 `1.0.0`，为事件协议版本，不是应用版本 |
| `accountId` | 源微信账号标识 |
| `streamId` | 本地该账号首次建立持久状态时生成的 UUID |
| `sequence` | 当前 stream 内严格递增的批次序号，从 1 开始 |
| `syncId` | 一次完整本地观察产生的同步批次组 UUID |
| `mode` | `initial` 或 `delta` |
| `batchIndex` / `batchCount` | 从 0 开始的组内索引，以及总批次数 |
| `observedContactCount` | 本地观察到的总数量，仅用于诊断；不是删除依据 |
| `contacts` | 本批需要幂等更新的联系人；不包含未变化的联系人 |
| `source` / `platform` | 数据来源和客户端平台 |

事件 ID 为 `contacts:<streamId>:<sequence>`。序号不由内容摘要生成，因此
备注 A → B → A 是三个不同的变更。重试使用已经落盘的同一事件 ID 和完整 payload，
不得从新的本地快照重建同一事件。

## 持久化与确认边界

私有数据目录 `contact-sync.sqlite3` 保存账号 stream、序号、联系人字段摘要和待发送事件。
这些是 Connector 自身的同步进度，不是服务器业务数据的备用来源。
同一 SQLite 事务提交新的摘要和全部对应待发送事件，使用 FULL 同步。
事件经 Bridge Agent 接收确认后逐批删除；这是传输确认，不代表 CRM 业务成功。
CRM 的失败重试、幂等和完成状态由接收端负责。

先排空已有发送队列，再读取下一次变化。网络持续失败时只保留这一组待发送数据，
不会每个轮询周期再追加一整份通讯录。已确认批次在重启后不再发送；确认丢失的批次
可能重复发送，消费者必须去重。联系人数据库错误、空的非末尾分页、计数不一致、
重复 ID、分页期间账号或 token 变化都会阻止建立新基线。

联系人状态不与消息游标共用文件。`--reset-state` 只重置消息游标；不会删除联系人
基线。`--dry-run` 使用内存联系人状态，不消耗实际待发送队列。
不自动清空损坏的联系人状态；错误应报告并保留原文件供恢复。
本地状态丢失时会创建新 stream 并重新初始化，消费者必须进行有审计的 stream 切换，
不能将其当作原 stream 的后续序号。

旧 `state.json` 的 `contact_snapshot_token` 只有文件检查点，无法重建逐联系人摘要；
首次升级需要一次新的批量初始化，不能用旧 token 假装已经同步了增量基线。

## 消费者和切换前置条件

1. 新接收端订阅 `contactsChanged`，支持批量幂等 upsert，使用可信工作区与账号上下文。
   不要把新 payload 转发到旧 `contact-snapshot-events` 方法。
2. 同一 stream 按序处理；乱序批次等待缺失批次或按有记录的恢复流程处理，不能仅因为
   收到更高全局序号就丢弃包含其他联系人的旧批次。重复 eventId 不重复创建 CRM 线索。
   同步组只有所有批次成功后才标记业务完成。
3. `initial` 用于建立联系人资料，不应逐个启动旧快照工作流。需要创建的 CRM 线索
   由业务接收端按账号和联系人唯一键幂等处理，失败不能丢失待执行动作。
4. 两种 mode 都不能按“本轮没有出现”批量标记联系人失效。联系人字段更新与 CRM
   人工维护字段的归属应由业务端明确处理。
5. 切换时隔离旧 `contactSnapshotChanged` 任务，阻止旧 `completed` 在新状态建立后
   执行批量失效。对账与受控终止属于平台运维，不由 Connector 删除平台队列。
6. 先验证新接收端，再发布和安装 Connector。没有新订阅时宿主可能接收事件但没有
   业务消费者，因此仅凭 HTTP 接收成功不能宣称升级验收完成。

本次 Connector 改动不自动升级销售微信 Bundle，不清理平台积压，不替代事件中心的
公平调度修复。上述消费者条件未满足时不得推广安装。

## 验收

- 1 万联系人初始化为有界批次；后续无变化为 0 条事件。
- 修改一个备注、新增一个联系人、源删除标记变化均只发送对应变化。
- 备注 A → B → A 均被记录，数据库文件时间变化不重复上报。
- 发送中途重启、网络失败、确认丢失均保留相同的事件身份与内容。
- 快照读取失败不改变基线；账号切换后状态互相隔离，切回不重新初始化。
- 联系人接收端故障时，消息采集仍独立推进。
- 接收端集成验收须另行证明批量入库、乱序/重复处理、CRM 幂等和旧任务隔离。
